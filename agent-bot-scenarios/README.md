# SlideEdu Agent Bot — сценарии меню/форм для Chatwoot

Кастомный Agent Bot на Node.js/Express, повторяющий флоу с вашего скриншота/видео
("Список тем для вопросов" → подменю → пошаговая форма → передача специалисту),
но без Rasa и без Enterprise-плана. Agent Bot API — обычная community-фича
Chatwoot (`app/models/agent_bot.rb`, `bot_type: webhook`), доступная бесплатно
на self-hosted.

## Как это устроено

```
Виджет/чат  --messages-->  Chatwoot  --webhook (message_created/updated)-->  этот сервис
                                <--- POST /conversations/:id/messages  ---
```

Chatwoot присылает на `outgoing_url` бота вебхук при каждом входящем сообщении
и при каждом клике по кнопке (это тоже `message_updated`, т.к. клик просто
патчит `content_attributes.submitted_values` у уже показанного сообщения —
см. `app/controllers/api/v1/widget/messages_controller.rb#update`). Сервис
разбирает событие, ведёт диалог по дереву сценария (хранится в Postgres, см.
раздел "Файлы" ниже) и шлёт ответ обратно через Application API, используя
собственный токен бота.

Файлы:
- Дерево сценария (чистые данные) хранится в Postgres, таблица
  `agent_bot_flow_versions` (см. `db/schema.sql`) — append-only: каждое
  сохранение из `/admin` добавляет новую строку, ничего не перезаписывая, это
  и есть история версий (см. раздел "Редактор сценария" ниже).
  **Редактировать его обычно не нужно вручную** — для этого есть визуальный
  редактор `/admin`. Формат содержимого см. в `src/flowStore.js` (там же
  валидация). Локальный файл `src/flows.json` больше не читается движком —
  оставлен только как справочный пример структуры/фикстура для тестов.
- `src/db.js` — пул подключений `pg` к Postgres (`AGENT_BOT_DATABASE_URL`).
- `src/flowStore.js` — чтение/запись/валидация дерева сценария в Postgres, с
  синхронным in-memory кэшем (правки из `/admin` подхватываются движком сразу,
  без рестарта процесса — `getFlows()` остаётся синхронной для `engine.js`,
  под капотом кэш обновляется при каждом сохранении/`reloadFlows()`).
- `src/engine.js` — движок state machine (навигация меню/формы, "Назад"/"Главное меню").
- `src/chatwootClient.js` — обёртка над Chatwoot Application API.
- `src/store.js` — состояние диалогов (сейчас in-memory, для прода — замените на Redis).
- `src/server.js` — вебхук-эндпоинт, раздача собранного фронтенда `/admin` и
  `/dashboard`, их JSON API, проверка подписи.
- `web/` — исходники фронтенда `/admin` и `/dashboard` на Vue 3 (Composition
  API, `<script setup>`), собираются через Vite в `dist/` (см. "Фронтенд
  (Vue)" ниже). `dist/` не коммитится — собирается заново на каждом деплое.

## Установка

```bash
cd agent-bot-scenarios
npm install
cp .env.example .env
```

## 1. Создать Agent Bot в Chatwoot

Локально:
```bash
cd ~/code/chatwoot
RAILS_ENV=development bundle exec rails console
```
На дроплете:
```bash
sudo su - chatwoot -c "cd /home/chatwoot/chatwoot && RAILS_ENV=production bundle exec rails console"
```

Внутри консоли:
```ruby
account = Account.find(1) # локально — Acme Inc; на дроплете — ваш slideedu, id=5
bot = AgentBot.create!(name: "SlideEdu Scenario Bot", outgoing_url: "http://<адрес-этого-сервиса>:8000/webhook")
bot.access_token.token   # <- сохраните, это CHATWOOT_BOT_TOKEN
bot.secret               # <- сохраните, это AGENT_BOT_SECRET (необязательно, но желательно)

inbox = account.inboxes.first # или найдите нужный: account.inboxes.find_by(name: "...")
AgentBotInbox.create!(inbox: inbox, agent_bot: bot)
```

`outgoing_url` должен быть **доступен из Chatwoot**:
- Локально (Chatwoot и бот на одном Mac) — `http://localhost:8000/webhook` подойдёт.
- На дроплете — либо запустите сервис прямо на дроплете (`http://localhost:8000/webhook`,
  раз Chatwoot тоже там), либо, если сервис в другом месте — публичный URL,
  доступный с дроплета.

## 2. Заполнить `.env`

```
CHATWOOT_BASE_URL=http://localhost:3000        # или http://188.166.123.233:3001 на дроплете
CHATWOOT_ACCOUNT_ID=1
CHATWOOT_BOT_TOKEN=<bot.access_token.token>
AGENT_BOT_SECRET=<bot.secret>
AGENT_BOT_DATABASE_URL=postgresql://user:password@host:5432/dbname
```

`AGENT_BOT_DATABASE_URL` обязателен — без него `src/db.js` бросает исключение
при старте. Дерево сценария хранится в этой базе (таблица
`agent_bot_flow_versions`), а не в файле на диске. Перед первым запуском:

```bash
psql "$AGENT_BOT_DATABASE_URL" -f db/schema.sql   # создаёт таблицу + индекс, идемпотентно (IF NOT EXISTS)
```

Таблица должна содержать хотя бы одну строку до старта процесса —
`flowStore.init()` иначе бросает исключение с понятным сообщением
("сначала засейдите таблицу") и процесс не поднимется. Для первого сидирования
с существующего `flows.json`:

```bash
AGENT_BOT_DATABASE_URL=... node -e "
  const fs = require('fs');
  const flowStore = require('./src/flowStore');
  flowStore.saveFlows(JSON.parse(fs.readFileSync('src/flows.json', 'utf8')), { createdBy: 'seed' })
    .then(() => process.exit(0));
"
```

Можно использовать ту же Postgres, что и сам Chatwoot (отдельная таблица,
никак не пересекается со схемой Rails) — так и сделано на дропле
(`chatwoot_production`).

## Роутинг по категории pre-chat формы

У инбокса включена pre-chat форма с обязательным полем "Категория" (custom
attribute `type`, список: Slideedu, Logo-chat, Календарь логопеда,
Техническая поддержка, Финансовые вопросы). До этой правки бот на любое
первое сообщение всегда открывал `main_menu` — а это дерево целиком про
финансы, поэтому клиент, выбравший, например, "Техническая поддержка", видел
те же финансовые кнопки, что и выбравший "Финансовые вопросы".

Теперь `engine.js#startFlow` перед показом стартового узла спрашивает у
Chatwoot (`GET /conversations/:id`, `custom_attributes.type` — это именно
`custom_attributes`, НЕ `additional_attributes`, см. комментарий у
`getConversation` в `chatwootClient.js`, там же объяснение, почему их легко
перепутать) выбранную категорию и открывает СВОЙ узел для каждой:

- "Финансовые вопросы" → `main_menu` (исходное финансовое дерево);
- "Календарь логопеда" → `calendar_intro` (ID / проект / описание проблемы);
- "Техническая поддержка" → `tech_intro` (описание проблемы / номер AnyDesk);
- "Logo-chat" → `logo_intro` (ФИО / проект / описание);
- "Slideedu" → `slideedu_intro` (ФИО / проект / описание);
- категория не задана (старые диалоги без pre-chat формы) → как раньше,
  `main_menu`.

Для всех нефинансовых категорий уже настроены и правила автоматизации
Chatwoot (Settings → Автоматизация: метка + канонический текст — например,
AnyDesk-инструкция для "Техническая поддержка"), и теперь ещё и своя короткая
форма бота — оба ответа приходят клиенту, это осознанное решение, не баг.

Список категория → узел — `CATEGORY_ENTRY_NODE` в `engine.js`. Если появится
ещё одна категория в pre-chat форме (Settings → Источники → Web chat →
"Форма, показываемая перед стартом диалога") без записи в этом объекте — бот
для неё молчит (безопасный дефолт), сначала добавьте ветку через `/admin`,
потом впишите `'Название категории': 'id_узла'` сюда.

## Соответствие Freshchat

Текущее дерево сценария (см. "Файлы" выше — теперь в Postgres, `src/flows.json`
оставлен только как фикстура) повторяет структуру бота "Finance AI" в
Freshchat (10 веток с главного меню): Запись на консультацию, Проблема с
платежами (→ Неправильная сумма / Не учтен бонус), Получение финансовых
документов (→ Справка о доходах / Оформление инвойса / Выписка ЗП за период),
Вопросы по ведению ФОП, Общие финансовые вопросы. "Смена реквизитов" узлы
тоже есть в файле, но, как и в самом Freshchat сейчас, не подключены к
главному меню — специально, чтобы было видно, как включать/выключать ветки
одной строкой в `main_menu.options`.

Ветки "Неправильная сумма", "Не учтен бонус" и "Общие вопросы" сверены с
билдером Freshchat узел-в-узел. Ветки "Справка о доходах", "Оформление
инвойса", "Выписка ЗП за период", "Смена реквизитов" и "Вопросы по ведению
ФОП" восстановлены по общему шаблону (email → должность → руководитель → ФИО
→ доп.поля → заявка) и названию — я не смог открыть их внутренний список
полей в билдере Freshchat в рамках сессии (та самая проблема с зависанием
экрана, требующим ручного рефреша). Логика и назначение группы верны, но
точные формулировки специфичных для этих веток вопросов стоит свериться с
Freshchat и поправить при необходимости — теперь это можно сделать прямо в
`/admin`, без правки кода.

## Типы узлов

Кратко: `menu`,
`question` (поле `field: { name, type }`, type — `text` / `email` /
`select`), `message` (проходной, без ответа пользователя), `link`
(терминальный, информационный — например, ссылка на календарь, без заявки),
`end` (терминальный без заявки — например, "обратитесь к куратору"), `submit`
(создаёт заявку: текст + назначение команды + резолв диалога).

Поле `email` использует `content_type: input_email` — нативный тип Chatwoot
(как в Freshchat), плюс движок ещё раз проверяет формат при получении
ответа и переспрашивает при ошибке. Поле `select` (например, валюта)
рендерится как quick-reply меню, а не свободный текст.

## Передача человеку-специалисту

На последнем шаге (`type: 'submit'`) бот отправляет текст, назначает диалог
на команду (`group` в `flows.js` → `chatwootClient.assignTeamByName`) и
резолвит диалог. **Команды нужно создать в Chatwoot заранее** (Settings →
Teams) с точно такими же названиями, как `group` в `flows.js` — они взяты
1-в-1 из названий групп в Freshchat (например, "Финансы - Поступила
неправильная сумма ЗП"), чтобы маршрутизация совпадала. Если команда с таким
именем не найдена — бот пишет предупреждение в лог и просто не делает ассайн
(тикет всё равно резолвится и текст заявки виден в диалоге).

Старый механизм (`addLabel`) тоже остался в `chatwootClient.js` — можно
использовать как запасной/дополнительный вариант поверх team-ассайна.

**Автоназначение на конкретного оператора.** Поле "Оператор (автоназначение,
необязательно)" на узле `submit` в `/admin` (`node.assignee` в дереве
сценария) назначает диалог на конкретного агента по имени или email —
`chatwootClient.assignAgentByName`, тот же паттерн, что и у команд
(`assignTeamByName`), только на уровне человека, а не отдела. Не заменяет
`group`: команда по-прежнему проставляется для отчётности/фильтров, `assignee`
дополнительно кладёт заявку в очередь конкретного оператора. Если имя/email
не совпало ни с одним агентом аккаунта — предупреждение в лог, назначение на
команду и сам сабмит при этом не страдают.

## Тикеты и несколько заявок от одного клиента

- **Номер заявки** — у каждого `conversation` в Chatwoot есть `display_id`,
  последовательный номер по аккаунту. Он и есть номер тикета, виден в UI и
  в API/вебхуках как `conversation.id` в `webhook_data`.
- **Диалог после `submit` остаётся Open.** Бот больше не резолвит его сам
  (в отличие от более ранней версии). Причина: мгновенный резолв на
  submit ломает отчётность Chatwoot ("время решения" считается от момента
  resolve, а не от реальной обработки агентом) и прячет свежую заявку из
  дефолтного фильтра "Открыт" — приходилось городить приоритет+папки поверх,
  что оказалось лишним. Сейчас всё просто: заявка Open, пока агент её не
  закроет вручную, отчёты и фильтры Chatwoot работают без единой поправки.
- **Несколько одновременно открытых заявок от одного клиента, без
  смешивания.** Штатно у виджета есть кнопка "Start a new conversation"
  (`app/javascript/widget/components/ChatFooter.vue`), которая переводит
  экран на pre-chat форму — отправка этой формы **всегда** создаёт новый
  `Conversation` (`Api::V1::Widget::ConversationsController#create`), там
  нет проверки статуса предыдущего диалога. Раньше эта кнопка была видна
  только когда диалог resolved (`hideReplyBox` в `ChatFooter.vue`). Мы
  добавили рядом с обычным полем ввода отдельную всегда доступную кнопку —
  "Новая заявка" (виден, когда `conversationSize > 0`, т.е. после первого
  сообщения) — она дёргает тот же `startNewConversation()`, но независимо
  от статуса. Так клиент может открыть вторую (третью, ...) заявку, пока
  первая ещё не обработана — обе видны в Chatwoot как отдельные Open-диалоги
  со своими номерами, никакого резолва не требуется.
  Честный нюанс: сам виджет при повторном открытии окна чата всегда
  подгружает **последний** созданный диалог этого контакта
  (`Api::V1::Widget::BaseController#conversation` → `conversations.last`).
  Вернуться из окна виджета к более старой ещё открытой заявке нельзя — это
  ограничение однооконного UI виджета. Агенты это не касается — в самом
  Chatwoot все диалоги видны как обычно.
- **Статистика по клиенту** — теперь есть отдельный дашборд, см. ниже.

## Дашборд статистики

`GET /dashboard` на этом же сервисе (например, `http://localhost:8000/dashboard`)
— Vue-приложение (см. "Фронтенд (Vue)" ниже), данные тянет с `GET
/dashboard/api/data`. Три секции:

- **Клиент × тема** — по каждому контакту: сколько заявок и по каким командам
  (темам), когда была последняя. Считается из полного списка диалогов
  аккаунта (`GET /conversations`, все статусы, все страницы).
- **Среднее время ответа и решения** — по аккаунту в целом и по каждой
  команде, за последние 90 дней. Это не самодельный расчёт, а проксирование
  родного отчёта Chatwoot (`GET /api/v2/accounts/:id/reports/summary`) — там
  уже учтены рабочие часы, переназначения и т.п., пересчитывать вручную
  ненадёжно.
- **Тренд по неделям** — сколько заявок в неделю, с разбивкой по темам,
  посчитано из того же набора диалогов, что и первая секция (чтобы цифры
  между секциями не расходились).

**Нужен отдельный токен.** Отчёты Chatwoot (`/reports/summary`) доступны
только администратору аккаунта — токен самого бота (`CHATWOOT_BOT_TOKEN`) для
этого не подходит (у AgentBot нет роли "администратор"). Возьмите личный
API-токен админа: в Chatwoot → иконка профиля внизу слева → Profile Settings
→ Access Token → скопировать, и впишите в `.env` как `CHATWOOT_ADMIN_TOKEN`.
Без этой переменной `/dashboard` вернёт понятную ошибку вместо данных, сам
бот при этом продолжит работать как обычно.

Ограничение: выборка диалогов для "клиент × тема" и тренда capped на ~1000
диалогов (`MAX_PAGES` в `src/dashboard.js`) — защита от долгого запроса на
очень больших аккаунтах, поднимите константу при необходимости.

## Редактор сценария

`GET /admin` (например, `http://localhost:8000/admin`) — визуальный редактор
дерева сценария на Vue (см. "Фронтенд (Vue)" ниже), по аналогии с билдером
Freshchat: слева список узлов по веткам (с поиском), в центре — схема со
стрелками связей (узлы можно перетаскивать мышью, позиции сохраняются),
справа — форма редактирования выбранного узла (поля зависят от типа:
`menu`/`question`/`message`/`link`/`end`/`submit`). Кнопка "+ Добавить узел"
создаёт новый узел с указанным id и типом, кнопка "Удалить узел" — удаляет
(ссылки на него из других узлов после этого нужно поправить вручную —
редактор их не чинит автоматически).

Всё сохраняется одной кнопкой **"Сохранить всё"** — она шлёт всё дерево на
`POST /admin/api/flows`, сервер валидирует его тем же кодом, что использует
сам движок (`flowStore.validate` — проверяет обязательные поля по типу узла
и что все `next`/`options[].next` ссылаются на существующие id), и либо
сохраняет как новую версию в Postgres (`agent_bot_flow_versions`), либо
возвращает список ошибок без сохранения.

**Изменения применяются сразу**, без рестарта pm2-процесса и без отдельного
шага "опубликовать" — `engine.js` вызывает синхронный `flowStore.getFlows()`
на каждое сообщение, а этот кэш обновляется сразу же при сохранении из
`/admin` (см. `flowStore.js`).

**История версий и восстановление.** Кнопка "История" в тулбаре открывает
список всех сохранений (дата, автор — определяется живьём по тому же
Basic Auth токену через `GET /api/v1/profile`) с кнопкой "Восстановить" у
каждой записи. Хранение append-only: каждое сохранение (в том числе само
восстановление старой версии) добавляет новую строку, ничего не
перезаписывая и не удаляя — история никогда не теряется, "текущее" состояние
всегда просто строка с максимальным `id`. Резервные копии перед крупной
правкой больше не нужны — достаточно открыть "История" и восстановить нужную
версию в любой момент.

**Доступ — по личному токену администратора Chatwoot, не по отдельному
паролю.** Браузер спросит логин/пароль (Basic Auth) — логин можно ввести
любой (не проверяется), а в пароль нужно вставить свой личный access token
Chatwoot (Profile Settings → Access Token). Сервис на каждый запрос
проверяет этот токен живьём через Chatwoot API (`GET /webhooks` — эндпоинт,
доступный только администраторам аккаунта, см. `verifyAdminToken` в
`chatwootClient.js`) и пускает только тех, кто и так администратор в самом
Chatwoot — заводить отдельную учётку не нужно. Результат проверки кэшируется
на 5 минут, чтобы не дёргать Chatwoot на каждый клик в редакторе.

Список команд в поле "Команда (Chatwoot Team)" на узле `submit` берёт имена
живьём из `GET /teams` тем же токеном, что и `/dashboard`
(`CHATWOOT_ADMIN_TOKEN` в `.env`) — если он не задан, поле остаётся обычным
текстовым без подсказок. Поле "Оператор" рядом устроено так же — подсказки
имён берутся из `GET /agents` (тоже требует `CHATWOOT_ADMIN_TOKEN`, токену
бота этот эндпоинт запрещён платформой).

## Фронтенд (Vue)

`/admin` и `/dashboard` — два отдельных Vue 3 SPA (Composition API,
`<script setup>`), исходники в `web/admin/` и `web/dashboard/`, общая тема —
`web/shared/theme.css`. Собираются Vite'ом в один `dist/`
(`vite.config.js` — multi-page build: `admin.html` + `dashboard.html`, общие
JS/CSS чанки в `dist/assets/`). Node ничего не собирает на лету — только
отдаёт уже собранные файлы (`src/server.js`) и JSON через свои API.

`base: './'` в `vite.config.js` — не косметика, а обязательное условие:
сервис на дроплете стоит за nginx под путём `/agent-bot/` (see README
основного проекта/деплой), и относительные пути в собранном HTML — то, что
позволяет ассетам резолвиться корректно независимо от префикса прокси.
Абсолютные пути (`base: '/'`) увели бы запросы на корень
`slideedu-preview.space`, мимо прокси на бота.

Сборка — часть `deploy.sh` (`npm run build` после `npm install`), вручную
не нужна. Для локальной разработки с hot-reload:
```bash
npm start          # Node на порту из .env (обычно 8000) — API/вебхук
npm run dev:web     # Vite на 5173, проксирует /admin/api и /dashboard/api на Node
```
и открывать `http://localhost:5173/admin.html` /
`http://localhost:5173/dashboard.html` — Basic Auth для `/admin` при этом всё
равно проверяется настоящим Chatwoot (см. `verifyAdminToken`), прокси его не
подменяет.

## Продакшен-заметки

- **Состояние диалогов** сейчас в памяти процесса (`src/store.js`) — при
  перезапуске сервиса все незавершённые диалоги "забудутся". Для реальной
  нагрузки — вынести в Redis (интерфейс `get/set/clear` уже готов к замене).
- **Запуск на дроплете** — как обычный systemd-сервис или через `pm2`,
  аналогично тому, как у вас уже настроен Chatwoot (`chatwoot-web.1.service`).
  Простой вариант через pm2:
  ```bash
  npm install -g pm2
  pm2 start src/server.js --name slideedu-agent-bot
  pm2 save
  ```
- **HTTPS** — если сервис не на localhost относительно Chatwoot, поставьте
  его за тем же nginx с SSL, что и остальные сервисы на дроплете.
